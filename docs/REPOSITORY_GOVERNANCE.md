# 仓库治理与 Agent 协作规范

本文定义 Better Canvas 的任务入口、Agent 协作、Issue/PR 生命周期、分支约定和合并门禁。根目录 [AGENTS.md](../AGENTS.md) 是 Agent 工作入口；所有测试方法、测试层级、回归清单与验证证据标准统一以 [测试与验证规范](TESTING.md) 为准。

本项目当前只以 GitHub 仓库中的 Issue、Pull Request、代码、文档和 Actions 为工作依据。不建立或维护 Slack、社交媒体、论坛等外部社群监控流程。

## 1. 角色与责任

角色是每项任务必须覆盖的工作视角，不要求为每个角色配置独立机器人或账号。一个 Agent 可以承担多个角色，但实现完成后必须另做一次独立审查。

| 角色 | 主要责任 | 不应做的事 |
| --- | --- | --- |
| Issue 分流 | 检查是否可复现、补齐环境信息、关联重复项、标记范围与优先级 | 在信息不足时臆测根因或承诺交付时间 |
| 任务规划 | 把 Issue 转成可验证的验收条件，标出可能影响的模块、文档和测试 | 未确认需求就扩展范围 |
| 实现 Agent | 在独立分支中做最小必要改动，添加/更新测试并提供证据 | 直接向 main 推送，或顺手混入无关重构 |
| Review / QA Agent | 站在非作者视角检查 diff、回归风险、安全边界、测试覆盖和文档一致性 | 只看作者摘要，或把未运行的测试报告为通过 |
| 文档 / 发布维护 | 维护用户文档、功能矩阵和发布版本一致性 | 把“代码已实现”写成“已在 Obsidian 中验证” |

小任务可以合并角色；安全、文件持久化、Portal 同步、MCP/外部请求、发布工作流等高风险变更，必须明确记录独立审查结果。

## 2. 项目事实的唯一来源

- README.md：用户可见的功能、安装、配置、已知限制和开发入口。
- docs/TESTING.md：环境预检、测试层级、项目专项回归清单和证据要求。
- docs/INTEGRATION_MATRIX.md：功能实现程度、兼容性、尚未覆盖的行为。
- INTEGRATION_STATUS.md：当前集成/验证状态；只有状态确有变化时才更新。
- GitHub Issue：需求、缺陷、讨论结论和验收条件的工作入口。
- GitHub Pull Request：改动说明、审查讨论、CI 与测试证据。
- GitHub Actions：实际执行过的自动化检查及其对应 commit。

遇到冲突时，先确认当前源码和实际测试证据；不要只依据旧文档或 Issue 评论推断现状。文档可以描述未知和待验证事项，不应为了显得完整而推测。

## 3. Issue 入口与分流

新工作原则上先有 Issue，再开始非平凡实现。极小的拼写或纯文档修正可以直接开 PR，但 PR 必须解释原因并给出验证结果。使用仓库的 Bug Report 与 Feature Request 表单；不要要求提交者公开完整的私密 Canvas、Vault 内容、API Key、日志中的令牌或个人数据。

分流时完成以下动作：

1. 识别类型：缺陷、功能、文档或维护。
2. 确认影响范围：Canvas 核心交互、Portal、PDF、AI、MCP、导出、设置或 CI/发布。
3. 判断信息是否足够复现；不足时标记为需要补充信息，并提出具体问题。
4. 写清可验证的预期行为、实际行为和验收条件；关联重复 Issue、相关 PR 或已知限制。
5. 给出合理优先级，并说明判断依据。优先级不是对完成日期的承诺。

### 推荐标签

先检查现有标签再复用；如果需要，可在 GitHub 仓库设置中补齐以下最小标签集。不要通过批量改标签破坏已有分类。

| 维度 | 建议值 |
| --- | --- |
| 类型 | type: bug、type: feature、type: docs、type: maintenance |
| 范围 | area: canvas、area: portal、area: pdf、area: ai、area: mcp、area: export、area: settings、area: ci-release |
| 优先级 | priority: P0、priority: P1、priority: P2、priority: P3 |
| 状态 | status: needs-triage、status: needs-info、status: blocked、status: ready |

优先级含义：

- P0：明确的安全问题、数据丢失、严重发布故障或影响广泛的核心功能失效。立即通知维护者并暂停有风险的发布。
- P1：主要工作流中断，且没有合理替代方案。
- P2：普通缺陷、兼容性问题或已确认的功能需求。
- P3：低影响体验改进、可选增强或非紧急文档工作。

Issue 生命周期：新建 → 分流 →（需要信息 / 已就绪 / 暂缓）→ 关联 PR → 验证 → 关闭。需求重复时链接主 Issue；不计划处理时说明理由。除非已有明确证据表明已解决，不要仅因为暂时无法复现就关闭缺陷。

## 4. 分支与并行协作

- 默认分支为 main。Agent 不直接提交或推送到 main，不自行绕过审查或 CI。
- 分支命名建议：fix/123-short-topic、feat/123-short-topic、docs/123-short-topic、chore/short-topic。数字对应 Issue；没有 Issue 的小型维护工作可省略编号。
- 一个分支和一个 PR 应聚焦一个目标。大型需求先拆成有依赖顺序的 Issue/PR。
- 并行任务应使用各自分支，并事先约定文件边界。不要让两个 Agent 同时覆盖同一文件；整合前分别检查每个分支的差异。
- 开始任务前先检查当前分支、工作区状态和目标基线；不得覆盖未提交的用户更改。
- 如需求、验收条件或风险发生改变，先在 Issue/PR 记录决策，再修改实现计划。

## 5. Pull Request 与审查门禁

PR 描述必须说明：解决的问题、主要改动、关联 Issue、行为变化、执行过的检查、未执行的验证、已知风险和必要的文档更新。功能完成不意味着可以跳过回归测试。

合并前至少满足：

1. 改动范围和验收条件一致；没有夹带无关格式化、大规模重命名或未解释的生成文件。
2. 相关 CI 成功，且结果对应待合并的 commit。当前自动检查包括 typecheck、Vitest 和 production build；具体以 workflow 实际步骤为准。
3. Review 已检查完整 diff，而不只是 PR 摘要；涉及同类功能时要搜索可能遗漏的相邻实现。
4. 用户可见行为、配置、命令、快捷键、格式或限制发生变化时，同步更新相关文档。
5. 如涉及 Obsidian 内部 API、Canvas 原生拖动/渲染、Portal 文件同步、PDF 坐标、主题/DOM、Vault 持久化或真实服务请求，必须清楚标记桌面端/运行时验证是通过、失败还是未执行。
6. 所有需要解决的 Review 讨论均已处理；由维护者决定是否合并。

除非维护者对当前任务作出明确授权，Agent 负责准备 PR 和证据，不自行合并或发布。

## 6. 高风险改动的额外检查

Review 以下改动时，要特别检查整个 diff 及其副作用：.github/workflows、权限与发布脚本、npm 依赖和安装脚本、构建配置、网络请求与外部 URL、API Key/令牌处理、Vault 文件读写、MCP 工具调用、本地进程启动、HTML 沙盒和导入/导出逻辑。

必须确认：

- 没有新增不必要的数据外传、遥测、凭据访问或静默文件修改。
- 错误处理不会把读取失败误当成空数据或成功，也不会破坏原始 Canvas 的未知字段。
- 测试不访问真实用户 Vault，不依赖真实付费 API，不在日志、fixture 或截图中暴露密钥。
- 新增依赖有明确的必要性，并检查许可、供应链与维护状态。
- 对涉及工作流权限、release 或仓库设置的改动，PR 需指出所需的人工设置或权限；代码里写了规则不代表 GitHub 设置已启用。

## 7. 文档与功能状态维护

- 新增用户可见功能、设置项或快捷键：更新 README 的相关说明。
- 功能状态、兼容性、缺失能力或验证覆盖发生变化：更新 docs/INTEGRATION_MATRIX.md。
- 集成/发布状态发生实际变化：更新 INTEGRATION_STATUS.md。
- 仅重构且没有用户可见变化时，不要为了提交形式而改写大量文档。
- 任何“已验证”“兼容”或“修复完成”的表述都必须有对应证据。远程 CI 通过、单元测试通过和真实 Obsidian 运行时验证是不同结论。

## 8. 发布流程

当前 release workflow 由 v* 标签触发，会执行类型检查、单元测试、生产构建，并核对标签版本与 manifest.json 中的插件版本是否一致。发布前应确认：目标 commit 的 CI 成功、版本号已更新且与标签一致、安装包构建完整、发布说明准确。不要仅凭标签已创建就宣称发布成功；以 GitHub Actions 和 Release 页面中的实际结果为准。

对 main 的保护规则需要在 GitHub 仓库设置中实际启用。建议至少要求通过 PR 合并、要求 Build 检查成功、禁止强制推送和删除 main；多人协作时再启用必需审查和对话解决要求。本文只记录建议，不代表这些设置已被自动配置。

## 9. Agent 交接记录

完成实现或审查时，在 PR 描述或交接评论中使用以下格式：

- Issue / 目标：
- 分支与待审 commit：
- 改动摘要：
- 已执行检查：命令、结果、commit SHA
- 未执行检查：原因
- Obsidian 运行时验证：通过 / 失败 / 未执行，并注明版本与平台（如适用）
- 风险、限制与后续事项：

未运行的步骤必须写“未执行”或“受阻”，不要写成通过。测试报告必须对应被审查的确切 commit；如果提交后又改了代码，应重新运行受影响的检查。
